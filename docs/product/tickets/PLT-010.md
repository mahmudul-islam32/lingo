# PLT-010: Backend gateway, demo backend, email sign-up and log-in, session
**Owner:** dev-platform · **Priority:** P0 · **Depends on:** CTO-003, CTO-004, CTO-006, CTO-007 (backend gateway interfaces) · **Milestone:** v0.4.0

## User story
As a learner, I want to sign up and log in with my email and a password so that my
progress is saved across devices (US-PLT-06).

## Context
There is no hosted Supabase project yet (waiting on the owner, PD-022). The app talks to
the backend only through a **backend gateway** (interfaces defined by the cto in CTO-007).
This ticket ships two implementations and the switch between them:

- **`supabase`**: the real `@supabase/supabase-js` browser client.
- **`demo`**: an in-memory fake with the same behaviour, used by unit tests, e2e tests,
  local development and preview builds. It never sends a network request.
- **`off`**: no backend. Polyglow behaves exactly like v0.3.0 (guest only, no account
  entry points anywhere).

Real credentials are a configuration change only, with no code change. Log out (with its
final sync and data wipe) is in PLT-017 (PD-023). Migrating the guest's progress after
sign-up is PLT-013.

## Acceptance criteria
**Backend mode**
1. The mode comes from public env vars, as documented in `.env.example`:
   `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` both set → `supabase`.
   Otherwise `NEXT_PUBLIC_DEMO_BACKEND=1` → `demo`. Otherwise `off`. If only one of the two
   Supabase vars is set, the mode is `off` and one console warning names the missing
   variable (no crash). Unit tests cover all four cases.
2. A single exported helper (e.g. `useAccountsEnabled()` / `accountsEnabled()`) returns
   `true` for `supabase` and `demo` and `false` for `off`. Every later account entry point
   (PLT-013, PLT-016, PLT-017, PLT-018) uses it.
3. In `off` mode, `/signup` and `/login` show the heading "Accounts are coming soon",
   the text "You can keep learning as a guest. Your progress stays on this device." and
   a "Back to Learn" button. No form is rendered and no network request is made.
4. In `demo` mode every auth screen shows the note "Demo mode: accounts are stored on this
   device only." No request leaves the browser for auth (a Vitest test asserts `fetch`
   is never called). Demo accounts and their data survive a page reload (stored in
   `localStorage` under one documented key) and a test helper can reset them.
5. No secret or real project URL is committed. The anon key is the only Supabase value
   that reaches the client bundle.

**Sign up (`/signup`)**
6. The form has "Email" (`type="email"`, `autocomplete="email"`), "Password"
   (`autocomplete="new-password"`, 8–72 characters) with a "Show password" toggle
   (`aria-pressed`), and a primary "Create account" button. There are links "Already
   have an account? Log in" (→ `/login`) and "Continue as guest" (→ `/`).
7. Validation runs on submit. An empty or malformed email shows "Enter a valid email
   address." and a password shorter than 8 characters shows "Use at least 8 characters."
   Each message sits under its field (`aria-describedby`, `aria-invalid="true"`), and
   focus moves to the first invalid field. No request is sent while the form is invalid.
8. An email that already has an account shows "An account with this email already
   exists." with a "Log in instead" link that opens `/login` with the email filled in.
9. On success the learner is signed in at once. No email confirmation step in MVP
   (PD-023). The screen then calls the single post-auth step (`completeSignIn`). In this
   ticket that step navigates to Learn (`/`). PLT-013 replaces it with the account
   handover.

**Log in (`/login`)**
10. The form has "Email", "Password" (`autocomplete="current-password"`) with the same
    toggle, a primary "Log in" button, a "Forgot password?" link (→ `/forgot-password`,
    PLT-012), "New here? Create an account" (→ `/signup`) and "Continue as guest" (→ `/`).
11. A wrong email or password shows the single message "Email or password is
    incorrect." It never says which one was wrong. The email is kept and the password is
    cleared.
12. On success, the same `completeSignIn` step runs as in criterion 9.

**Both forms**
13. While a request runs, the primary button shows a spinner with "Creating account…" or
    "Logging in…", has `aria-busy="true"` and ignores further presses (one request per
    submit, tested).
14. A network failure or a 5xx error shows "Something went wrong. Please try again." in a
    `role="alert"` region. The entered email is kept.
15. When the device is offline the form shows "You're offline. Connect to the internet to
    log in." (or "…to create an account."), the primary button is disabled, and the form
    becomes usable again within 1 s of the `online` event, without a reload.
16. A signed-in learner who opens `/signup` or `/login` is redirected to `/`.

**Session**
17. `useAuthSession()` returns `{ status: "loading" | "signed_out" | "signed_in", userId,
    email }`, and changes when the learner signs in or out (in this tab and, through the
    client's storage events, in other tabs).
18. The session survives a page reload, and a reload while offline still reports
    `signed_in` (the session is read from storage, with no network needed). Tokens refresh
    on reconnect. A refresh that fails for good reports `signed_out`.
19. The gateway's auth methods (`signUp`, `signIn`, `signOut`, `getSession`,
    `onAuthStateChange`) pass one shared behaviour test suite that runs against the demo
    backend in CI. The same suite can run against a local Supabase stack
    (`supabase start`) when the env vars are set, and is skipped otherwise.

**Quality**
20. Mobile-first: no horizontal scrolling at 375 × 667. The primary button stays visible
    when the on-screen keyboard is open (the form scrolls). Every control can be reached
    and used with the keyboard. There are no serious or critical axe violations on
    `/signup` and `/login` (empty, error and offline states), in both themes.
21. Playwright (demo mode, mobile): sign up with a new email → Learn, reload, still signed
    in (checked via a visible signed-in marker or the session hook test id). Then a
    second context logs in with a wrong password and sees "Email or password is
    incorrect."

## Out of scope
- Google sign-in (PLT-011), password reset (PLT-012), guest → account migration (PLT-013)
- Log out UI and data wipe (PLT-017; the gateway's `signOut` exists here)
- Any link to these screens from Learn, Profile or onboarding (PLT-013, PLT-016,
  PLT-017, PLT-018). After this ticket the routes exist but nothing links to them yet.
- Magic-link sign-in, email confirmation, Apple sign-in (Phase 2, PD-023)
- Account deletion (later; ADR-003 cascade is ready)

## UX notes
- **Layout:** full-screen auth layout without bottom navigation. Polyglow wordmark and a
  small Lumi (idle pose) at the top, heading ("Create your account" / "Welcome back"),
  form, then secondary links. Max width ~24rem, centred.
- **Loading:** a spinner in the primary button only. No page skeleton (the forms are
  static).
- **Empty:** fields empty with visible labels (not placeholder-only labels).
- **Error:** inline field errors plus one `role="alert"` summary for server errors. Kind
  copy, no blame.
- **Offline:** the offline banner (PLT-006) plus an inline note above the button. The
  button is disabled, not hidden.
- **Success:** no success screen. The learner goes straight on (Learn, or the handover
  screen from PLT-013).
- **Demo note:** small muted text under the heading, contrast AA in both themes.
