# GAM-015: Smart review selection rule, progress rules for review results, Practice "Review" card
**Owner:** dev-gamification · **Priority:** P1 · **Depends on:** CTO-019, GAM-012 ·
**Milestone:** v0.5.5 Smart review · **Decisions:** PD-065, PD-071 §2, PD-079, PD-080, PD-081

## User story
As a learner, I want the Practice tab to offer a short review of the exercises I got wrong
or haven't seen for a while so that I remember what I learned instead of only replaying
whole lessons (US-SR-01, US-SR-03).

## Acceptance criteria
Names follow CTO-019 and its ADR. "Outcome" = one stored `ExerciseOutcome`; its date is the
`localDate` of the result that holds it.

### Rule (`selectReviewItems`, pure, `src/features/gamification/rules/`)
1. **Eligible exercises:** every `(lessonId, exerciseId)` of the active course with at least
   one `correct` or `incorrect` outcome, whose `exerciseType` is in
   `REVIEW_EXERCISE_TYPES`, and whose lesson is still in the course manifest. `skipped`
   outcomes are ignored. Exercises the learner never answered are never selected.
2. **Per exercise:** `lastSeen` = date of the latest counted outcome; `correctRun` = number
   of `correct` outcomes in a row at the end of its history (ordered by result
   `completedAt`). `interval` = 0 days when `correctRun = 0`, else
   `reviewIntervalsDays[min(correctRun, length) − 1]`. `dueDate = lastSeen + interval`;
   the exercise is **due** when `dueDate ≤ today`.
3. **Order:** due exercises first, then not-due ones. Within each group: `correctRun`
   ascending, then `dueDate` ascending, then course order of the lesson, then the
   exercise's position in its latest result's outcomes, then `exerciseId`. The output keeps only the first
   candidate per `exerciseId` (no two items with the same id in one session).
4. Returns `{ candidates, dueCount, eligibleCount }`. `candidates` is the full ranked list
   (the route takes the first `reviewSessionSize` that load, PLT-029); `dueCount` counts due
   eligible exercises.
5. Worked examples are unit tests (today 2026-12-10, intervals [1, 3, 7, 14, 30]):
   A wrong on 12-09 → due; B right on 12-09 → run 1, due 12-10, due; C right 12-08 and 12-09
   → run 2, due 12-12, not due; D wrong 12-01, right 12-02 and 12-05 → run 2, due 12-08,
   due; E right 5 times, last 11-01 → due 12-01, due; F right 6 times, last 11-20 → interval
   30, due 12-20, not due; G only skipped → not eligible; H a `speak` exercise → not
   eligible; I a lesson no longer in the manifest → not eligible. Expected order A, B, D, E,
   C, F; `dueCount` 4; `eligibleCount` 6.
6. Results from other courses are ignored; review results' outcomes count like any other
   (they point to source lessons, CTO-019 criterion 2). 100 % branch coverage of the rule.

### Progress rules for review results (CTO-019 criterion 8)
7. `computeUserProgress` counts a review result's XP in total XP, today's XP, the daily goal
   and the streak, and never puts it in `completedLessonIds`. The same holds for
   `computePathNodes`, `buildPracticeList` and `useGoalPlan`'s completed-lesson count. Unit
   tests: a learner with 0 completed lessons and 1 review result has 0 completed lessons and
   its XP in today's total.

### Hook
8. `useReviewQueue({ courseId? })` (exported from `@/features/gamification`, default the
   active course) returns `{ status: "loading" | "error" | "success", candidates,
   dueCount, eligibleCount }` from `["progress", courseId]`, the course manifest and
   `useLocalToday`. It works offline and for guests and updates without a reload after a
   result is saved (query invalidation) and at local midnight. A read error is logged once
   (`console.warn`) and returns `status: "error"`.

### Practice "Review" card (`ReviewCard` in `src/features/path/practice/`)
9. `PracticeScreen` shows the card **above** the lesson list, under the intro text, for every
   course.
10. States:
    - **loading:** a skeleton the height of the card (no text flash);
    - **no history** (`eligibleCount = 0`): "Answer exercises in any lesson and they come back
      here for review." No button. Shown also when the lesson list is empty;
    - **due** (`dueCount ≥ 1`): heading "Review", line "<n> exercises are ready for review."
      (singular "1 exercise is ready for review.") and a primary link "Start review";
    - **caught up** (`dueCount = 0`, `eligibleCount ≥ 1`): heading "Review", line "You're all
      caught up. Review anyway to keep them fresh." and a soft link "Review anyway";
    - **error:** the card is not rendered; the lesson list works as before.
11. Both links go to `/review` (PLT-029). There is **no daily cap**: the link is shown after
    any number of review sessions today (PD-071 §2). Review is also offered at 0 hearts (the
    card never checks hearts, PD-065).
12. Copy rules: no "exam", "test", "pass", "failed", "weak" or "behind" in the card (RTL test
    over every state, whole words, case insensitive).

### Accessibility and mobile
13. The card is a `section` with the accessible name "Review"; the count line is plain text;
    the link's accessible name contains its visible text (WCAG 2.5.3), e.g. "Start review";
    reachable with Tab, works with Enter. No serious or critical axe violations in any state.
14. At 375 × 667 every state fits without horizontal scrolling or truncated text, with the
    first lesson card still starting above the fold in the "due" state; the link is at least
    48 px tall; v2 tokens only (CTO-016, AA contrast).
15. RTL tests cover criteria 8–13 for every state; existing Practice tests pass unchanged
    apart from the added card.

## Out of scope
- The `/review` route, loading the exercises, saving (PLT-029); the player and results in
  review mode (LES-023)
- A review count badge on the bottom nav, reminders, a review streak or review stats
- Per-word scheduling (it is per exercise), difficulty ratings, a "mark as known" button
- Review across courses

## UX notes
- **Placement:** Practice → title, hearts, intro, **Review card**, then the unit groups.
- **Tone:** kind and practical (PRD §8.3): "ready for review", never "weak words" or
  "mistakes to fix".
- **Empty:** existing learners see "no history" until they finish a lesson after the update
  (PD-080); the copy says how to fill it.
- **Success:** after a review, returning to Practice shows the new count without a reload.
