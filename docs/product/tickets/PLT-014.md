# PLT-014: Sync engine: idempotent push, pull and merge (no double XP)
**Owner:** dev-platform · **Priority:** P0 · **Depends on:** PLT-010 (gateway + demo backend), CTO-007, PLT-008 · **Milestone:** v0.4.0

## User story
As a learner, I want lessons I finish offline to sync automatically when I'm back online,
without ever losing or double-counting XP or streak days, so that my progress is the same
on every device (US-PLT-15; PRD goal G3, metric "offline reliability ≥ 99 %").

## Context
`src/lib/offline` already writes every fact change plus a `SyncQueueRecord` in one Dexie
transaction, and coalesces last-write-wins kinds (`sync-queue.ts`). This ticket builds the
`SyncEngine` (`src/contracts/api.ts`) in `src/lib/sync`, following ARCHITECTURE §4.3–4.4 and
ADR-003 §6. It talks to the backend only through the gateway (CTO-007). The demo backend
gets the server-side rules (insert-or-ignore, stale-update skip, earliest `joined_at`,
server cursor) so everything is testable without a hosted project (PD-022).

## Acceptance criteria
**When it runs**
1. The engine runs only when the device identity is an account **and** the backend mode is
   `supabase` or `demo`. For a guest, or in `off` mode, it makes zero gateway calls
   (tested) and `status()` is `idle`.
2. It runs on app start, on the `online` event, 2 s after the last enqueue (debounced; 3
   enqueues within 2 s give 1 run), every 60 s while the page is visible, and when
   `syncNow()` is called. It doesn't run while `navigator.onLine` is false. Then
   `status()` is `offline`.
3. Only one run happens at a time. A trigger during a run schedules exactly one follow-up
   run.

**Push**
4. Due records (`status: "pending"`, `nextAttemptAt ≤ now`) are pushed oldest
   `createdAt` first. Records not yet due are skipped in this run.
5. A record the server accepts, **or one that already exists there** (duplicate lesson
   result id), is removed from the queue and counted in `acceptedIds` / `duplicateIds`.
6. A network failure, a timeout or a 5xx response keeps the record `pending`,
   increments `attemptCount`, and sets `nextAttemptAt = now + min(2 s · 2^(attemptCount −
   1), 5 min)` (`SYNC_CONFIG`). `lastError` holds a short reason (≤ 500 chars). The
   remaining records are still attempted in the same run unless the device is offline.
7. A validation, constraint or RLS refusal (ADR-003 §6 error mapping) marks the record
   `rejected`. It is kept and never retried, is reported in `rejected`, and doesn't block
   other records.
8. An expired access token (401) is **not** a rejection. The engine refreshes the session
   once and retries the run. If the refresh fails, the records stay `pending` and
   `status()` is `error` (PLT-015 shows it).

**No double XP**
9. Pushing the same lesson result twice, or retrying after a lost response (the demo
   backend stores the row and then throws), leaves exactly one server row, removes the
   queue record, and leaves the local results unchanged. Total XP, streak and daily goal
   computed before and after are identical (tested).

**Pull and merge**
10. After the push, the engine pulls rows changed since `SyncMeta.lastPullAt`, which is
    always a **server** timestamp (lesson results by `created_at`, the others by
    `server_updated_at`), and stores the new cursor.
11. Pulled lesson results are added to Dexie only if their id isn't there yet (set
    union). Pulled settings, profile and hearts replace the local record only when their
    `updatedAt` is newer. The profile's `joinedAt` becomes the earlier of the two.
12. Every pulled row is parsed with the contract's zod schema. An invalid row is skipped
    and reported (no crash), and the rest of the pull still applies.
13. Applying a pull never creates new sync records (no echo back to the server).
14. When a pull changed something, the progress, settings, profile and hearts queries are
    invalidated, so Learn and Profile update without a reload. `lastPushAt` and
    `lastPullAt` are saved in `meta`.

**Status API**
15. `status()` / `subscribe()` report `idle`, `syncing`, `offline` or `error` (`error` =
    the last run left due records after a transient failure, or the session can't be
    refreshed). A successful run goes back to `idle`. `syncNow()` never throws.
    `pending()` lists the queue. A `useSyncStatus()` hook exposes the status and the
    pending lesson-result count (for PLT-015 and PLT-017).

**Demo backend and tests**
16. The demo backend's data side follows ADR-003: insert-or-ignore by id for lesson
    results; upserts for settings, profile and hearts that skip stale `updated_at`;
    `joined_at` only moves earlier; per-user isolation (user A can never read or write B's
    rows); a server clock for `created_at` / `server_updated_at`. One shared behaviour test
    suite covers these rules and can also run against a local Supabase stack when env
    vars are set (skipped otherwise).
17. Vitest with `fake-indexeddb` covers criteria 1–15, including backoff timing with
    injected `now`, coalesced settings (only the latest is pushed), a rejected record next
    to good ones, and **two devices**: device A completes a lesson and syncs, device B
    (same demo account) syncs and then shows the result. Its XP is counted once.

## Out of scope
- Any UI (status in the banner: PLT-015; unsynced warning on log out: PLT-017)
- Guest → account migration (PLT-013 calls `syncNow()` after it)
- Background Sync API / syncing while the app is closed (later, if data shows a need)
- Realtime subscriptions (Phase 2 leaderboards)
- Analytics events through the queue (PLT-019, needs a contract change)

## UX notes
No screens. The behaviour the learner notices: progress from another device appears on
Learn within one run of opening the app online, and nothing ever counts twice.
- **Loading / error / success:** exposed only through `useSyncStatus()` for PLT-015.

with a local stub). Runs in parallel with PLT-011, PLT-012 and PLT-016. It touches only
`src/lib/sync` plus the provider mount in `src/app/providers.tsx`. PLT-013, PLT-015 and
PLT-017 depend on it.
