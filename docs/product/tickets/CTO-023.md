# CTO-023: Are topics course data? Decision and, if so, the topic contract
**Owner:** cto · **Priority:** P1 · **Depends on:** CTO-008 · **Milestone:** v0.5.6 Life in
Germany topics · **Decisions:** PD-071 #5, PD-086

## User story
As the pm, I want topics stored and validated like the rest of the course content so that I
can map and change them in `/content` without a code change, and so that a wrong lesson id
fails CI instead of showing a broken row (US-TP-01).

## Product requirements (input to the decision)
- A topic belongs to **one course**. Only `en-de` has topics now; any course may have none.
- A topic has an id, an English title, a one-sentence description and an ordered list of
  lesson ids of **its own course**. It adds no content and never changes the path order,
  locks or XP (PD-064, PD-086).
- Works offline exactly like lessons (bundled, precached). Needs no server and is never
  synced, so `CONTRACTS_VERSION` stays 1 and nothing changes in `/supabase`.
- **pm preference:** topics are course data in `/content`, in a separate file per course
  (e.g. `content/courses/en-de/topics.json`), so that editing a topic doesn't bump
  `course.version` and doesn't rename the `audio-v<course.version>` cache. The cto may decide
  otherwise with a reason in the ADR.

## Acceptance criteria
1. **ADR-021** records the decision: topics are course data or not, where they live, how they
   are loaded, and the alternatives considered (inside `course.json`, a separate file, code in
   `src/features/path`). If the answer is "not course data", criteria 2–5 are replaced by the
   ADR's alternative and the pm and dev-gamification are told in the PR description.
2. A strict zod schema in `src/contracts` (e.g. `TopicSchema`, `CourseTopicsSchema`) with
   exported types: `id` (slug), `title` (1–30 characters), `description` (1–90 characters),
   `lessonIds` (3–12 slugs, no duplicates within a topic); at most 12 topics per course; topic
   ids unique within the course; unknown keys rejected.
3. The content test (`src/contracts/__tests__/content.test.ts` or a sibling) checks for every
   course that has topics: every `lessonId` is in that course's manifest; a lesson is in at
   most 2 topics; no topic lists a lesson of another course. A fixture with a wrong lesson id
   fails with a message naming the topic and the id.
4. The content layer exposes the topics of a course with a typed loader (e.g.
   `ContentRepository.getTopics(courseId)` plus a TanStack Query key in `queryKeys`), which
   returns `[]` for a course without topics and works offline (precached like lesson chunks).
5. A topics fixture for the German fixture course in `src/lib/content/__fixtures__` with at
   least 2 topics (one with lessons from 2 levels), for GAM-016's tests.
6. `ARCHITECTURE.md` §9 (Content) mentions the topics file and its rules in two lines or fewer.
7. `npm run typecheck`, `lint`, `test`, `build` pass; no change to `/supabase`, `CONTRACTS_VERSION`
   or any existing content file (the pm adds the real `en-de` file in CON-005).

## Out of scope
- The real topic data (CON-005)
- The Topics screen (GAM-016)
- Translating topic titles (Phase 3, localised UI, PD-031)
- Server storage or sync of topics
