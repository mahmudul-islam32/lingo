# CTO-018: A goal plan per course (contract and stored-data migration)
**Owner:** cto · **Priority:** P1 · **Depends on:** CTO-017, FIX-014 · **Milestone:** v0.5.5
(must be merged before v0.6.0's settings sync, PLT-010 / PLT-014) · **Decisions:** PD-071 §1,
PD-078

## User story
As a learner who switches between German and telc B1 Exam Prep, I want each course to keep
its own goal date so that a plan I made for one course never changes the numbers or the
target of the other (US-GD-01 … US-GD-04).

## Background
CTO-017 stores one `Settings.goalPlan` for the whole app. Since TELC-001 a learner can switch
courses in Profile, and the one plan then applies to whichever course is active:
- an "A2 by 12 Mar" plan made on German counts telc B1's A1 / A2 lessons after a switch;
- a telc "B1 by …" plan shows "Finish B1 by …" in Profile on German, while German's Learn
  shows "Set a goal date" (B1 has no content there) and the dialog preselects A2.

## Acceptance criteria
Names are proposals; the cto may rename them in the ADR. The behaviour is what is tested.

### Stored plans
1. Settings hold **at most one goal plan per course id**, e.g. `goalPlans: Record<Slug,
   GoalPlan>` (or another shape the ADR picks). Setting, changing or removing the plan of one
   course leaves every other course's plan unchanged (unit test with two courses).
2. The settings patch can set or clear the plan of **one** course without sending the
   others. A unit test shows: set course A → set course B → clear course A → only B is left.
3. **Migration of stored data:** a record with the old single `goalPlan` reads as a plan for
   the course that is active in that record (`Settings.courseId`, else `DEFAULT_COURSE_ID`).
   No plan is lost or duplicated. Records without a plan stay valid. If a Dexie version bump
   is needed, the ADR says so and an upgrade test covers it.
4. The old `goalPlan` field is either kept as a read-only fallback or removed; the ADR says
   which and for how long. Queued `settings` sync records written before CTO-018 still parse.

### Rule and status
5. `ComputeGoalPlan` keeps its inputs and output (one course, one plan). The callers pass
   the active course's plan. `GoalPlanStatus` is unchanged.

### Backend and docs
6. The Supabase `settings` column(s) match the new shape (nullable, CHECK on each plan as in
   ADR-015 §6, RLS unchanged), and `migrate_guest_to_account` carries every course's plan.
   No migration is run against hosted Supabase.
7. An ADR (next number, amending ADR-015) records the shape, the migration rule in
   criterion 3, the clear semantics, the consumer changes for GAM-014 and PLT-028, and the
   **conflict rule under settings last-write-wins**: today the whole settings record wins
   by `updatedAt`, so two devices editing different courses' plans could lose one edit. The
   ADR says whether v0.6.0 keeps that (acceptable: rare, recoverable by re-entering a date)
   or merges `goalPlans` per course, and PLT-014 inherits the choice.
8. `npm run typecheck`, `lint`, `test`, `build` pass; existing contract tests pass or are
   updated in the same PR, with the reason in the PR description.

### Added 2026-11-26 (PM-012, before work starts)
9. **Kept, not cleaned up:** a plan stored for a course id that is unknown to the registry,
   hidden, or has no levels (FIX-014's case) stays stored and valid and is simply not shown.
   Map keys are validated as slugs; an invalid entry makes the record invalid as any other
   bad field does today (fixture test).
10. `CONTRACTS_VERSION` stays `1`, or the ADR explains the bump and how queued `settings`
    records with `schemaVersion: 1` still parse (criterion 4).
11. A pure selector exported from the contracts, e.g. `goalPlanFor(settings, courseId)`,
    returns one course's plan and applies the migration rule of criterion 3, so GAM-014 and
    PLT-028 read plans the same way (unit tests: new shape, old single plan on the active
    course, old single plan asked for another course → `null`).

## Consumer tickets (written 2026-11-26, PM-012; start once this ticket is merged)
- **GAM-014** (dev-gamification): `useGoalPlan({ courseId })` reads that course's plan.
- **PLT-028** (dev-platform): the Profile row and dialog read and write the active course's
  plan; "Remove goal date" removes only that course's plan; the results row uses the
  lesson's course; e2e: set A2 on German, switch to telc B1 → "Not set" and the "Set a goal
  date" link; switch back → the German plan is there.
- **CTO-019** (cto, Smart review) edits the same contract files; merge CTO-018 first.

## Out of scope
- A date-only goal for courses without levels (Einbürgerungstest), PD-078 (later)
- Showing the plans of other courses in Profile or on Learn
- Any UI change (GAM-014, PLT-028)
- Making `startLevel` or `dailyGoalXp` per course (they stay global; revisit only if
  course switchers ask, PD-082)

## UX notes
No UI in this ticket. Learner-facing rule (PD-078): **the goal date always belongs to the
course you are on.** Switching courses shows that course's plan, or the "Set a goal date"
link if it has none, or nothing on a course without levels (FIX-014). Mobile 375 px and
accessibility: n/a in this ticket (no UI); GAM-014 and PLT-028 carry them.
