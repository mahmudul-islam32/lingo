# CTO-024: Connect the owner's hosted Supabase project and smoke-test accounts on it
**Owner:** cto · **Priority:** P0 · **Depends on:** owner items **O1, O2, O4** (O3 for Google);
PLT-010, PLT-012 … PLT-018 accepted on local Supabase; PLT-011 merged · **Milestone:** v0.6.0
Accounts and sync, **part B (owner's hosted project)** · **Decisions:** PD-085, PD-087

## User story
As the owner, I want accounts and sync to work on the real app so that my progress carries over
between my devices.

## Owner items this ticket waits for (see ROADMAP v0.6.0)
- **O1** Supabase project created; Project URL and anon (public / publishable) key given to the
  team. **Never** the service-role key or the database password in chat.
- **O2** A way to apply migrations without sharing secrets: the owner adds the CLI access token,
  project ref and database password as GitHub Actions secrets, or runs the runbook commands.
- **O3** Google OAuth client created and entered by the owner in the Supabase dashboard.
- **O4** The URL the app is served from (preview or public), for redirects and email links.

## Acceptance criteria
1. A runbook (`docs/architecture/hosted-supabase.md`) lists every step the owner and the cto do,
   in order, and where each value goes. It says in bold that the service-role key and the
   database password are never pasted into chat, issues, commits or logs.
2. All migrations in `/supabase/migrations` are applied to the hosted project through O2;
   `supabase migration list` (or the dashboard) shows the same list as `main`.
3. Hosted auth settings match `supabase/config.toml` except where PD-087 says otherwise: site URL
   and redirect URLs from O4 (incl. `/auth/callback`), minimum password 8, anonymous sign-ins
   off, **email confirmation on**.
4. The production (or preview) build has `NEXT_PUBLIC_SUPABASE_URL` and
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` set in the hosting environment, not in the repo. The Google
   flag is on only when O3 is done.
5. Smoke test on the hosted project with two test accounts, recorded in the release PR: RLS
   (account A can't read B's rows), sign up with email confirmation, log in, guest → account
   migration, offline → online sync, second device continue, password reset email arrives, log
   out. Google sign-in if O3 is done; otherwise the release notes say "Google sign-in follows".
6. The `accounts` e2e project runs green against the preview deployment, or the deviations are
   listed for PM acceptance.
7. No secret appears in the repository, the CI logs or the PR (checked with the repository's
   secret scanning or a grep for the service-role key prefix).

## Out of scope
- Custom SMTP sender for auth emails (owner item O5, before the public launch, not blocking
  v0.6.0)
- Public launch, analytics, account deletion (v1.0.0)

## UX notes
No new screens. With the flag on, the accounts UI from part A appears in the hosted build.
