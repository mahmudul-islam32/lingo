# GAM-003: XP totals and today's XP from saved results
**Owner:** dev-gamification · **Priority:** P0 · **Depends on:** GAM-002, PLT-008 · **Milestone:** v0.3.0

## User story
As a learner, I want my total XP and today's XP to add up every lesson I finish so that I
can see my effort grow (US-GAM-04, US-GAM-07).

## Context
GAM-002 already shipped the pure rules in `src/features/gamification/rules/`
(`calculateXp`, `computeStreak`, `loseHearts` / `refillHearts` / `viewHearts`,
`computeDailyGoalProgress`, `toLocalDate`). This ticket adds the missing aggregate rule
(`ComputeUserProgress` in `src/contracts/api.ts`) and the read hooks that every v0.3.0
screen uses. It adds no UI.

## Acceptance criteria
1. A pure function `computeUserProgress` implements the contracts type
   `ComputeUserProgress` and is exported from `@/features/gamification`. Its output passes
   `UserProgressSchema.parse`.
2. `totalXp` = the sum of `xpEarned` over all results of the course, including replays
   (PD-008). With no results it is 0.
3. `completedLessonIds` lists each lesson id with at least one result exactly once, and
   `lessonsCompletedCount` equals its length. Replaying a lesson does not raise the count.
4. `dailyGoal` comes from the existing `computeDailyGoalProgress` with the learner's goal
   and today's local date. `dailyGoal.earnedXp` is "today's XP".
5. `streak` comes from the existing `computeStreak` over the distinct `localDate`s of the
   results. `hearts` is the stored state after `refillHearts(state, now)`.
6. Results whose `courseId` differs from the input course are ignored.
7. The function contains no XP, heart or goal number literals (values come from the inputs
   and `GAME_CONFIG`).
8. A hook `useLocalToday()` returns the device-local date (`YYYY-MM-DD`) and updates
   without a reload: at local midnight while the app is open, and when the page becomes
   visible again (`visibilitychange`) on a different day.
9. A hook `useUserProgress(courseId)` returns `{ status: "loading" | "error" | "success",
   progress }`, reading results, hearts and settings through the `@/lib/offline` data
   layer (never Dexie directly). It re-derives when `["progress", courseId]` or
   `["hearts"]` is invalidated, so finishing a lesson updates totals without a reload.
10. Before onboarding has saved a daily goal, `useUserProgress` uses
    `GAME_CONFIG.defaultDailyGoalXp` as the goal instead of failing.
11. If the results can't be read, the hook returns `status: "error"` and does not throw;
    callers decide the fallback.
12. Unit tests (table-driven) cover: no results; one perfect lesson (15 XP total, 15
    today); a replay of the same lesson (30 total, still 1 lesson completed); results
    from yesterday and today (only today's XP in `dailyGoal`); results of another course
    ignored; hearts refilled lazily at `now`; 1,000 results computed in under 50 ms.
13. Hook tests cover: loading → success; error state; `useLocalToday` changes at a
    simulated local midnight and on `visibilitychange`.
14. Branch coverage of `progress.ts` is 100 %.

## Out of scope
- Any screen or component (GAM-006, GAM-007, GAM-008, LES-010)
- Streak status labels (GAM-004)
- Hearts mutations (GAM-005)
- Syncing results (PLT-014, v0.4.0)
- XP history or charts (Phase 2)

## UX notes
No UI. States exposed to consumers:
- **Loading:** `status: "loading"` (consumers show their own skeleton).
- **Error:** `status: "error"` (consumers show a fallback, never a crash).
- **Empty:** a new learner gets `totalXp: 0`, `lessonsCompletedCount: 0`, streak 0, full
  hearts, `earnedXp: 0`.
- **Success:** full `UserProgress`.

## Parallel work

time as GAM-005 (different files; both add lines to the gamification barrel). GAM-004,
GAM-006, GAM-007, GAM-008 and LES-010 build on this hook.

No contract change needed.
- **Reuse (GAM-002, do not rewrite):** `computeStreak(distinctDates, today)`, `refillHearts(state, now)`, `computeDailyGoalProgress(results, goalXp, today)`, `toLocalDate(now, timeZone)` from `rules/`. `totalXp` = plain sum of `result.xpEarned` (the rules' `totalXp(breakdown)` is per-result, don't confuse them).
- **Files:** `src/features/gamification/rules/progress.ts` (+ `__tests__/progress.test.ts`, export from `rules/index.ts`), `src/features/gamification/data/queries.ts` (query-option factories `progressQuery(courseId)`, `heartsQuery()`, `settingsQuery()`, shared with GAM-005), `src/features/gamification/hooks/use-local-today.ts`, `hooks/use-user-progress.ts`, `hooks/__tests__/…`, barrel lines in `src/features/gamification/index.ts`.
- **Data access:** `const s = await getLocalSession()` from `@/lib/offline`, then `s.progress.listLessonResults(courseId)`, `s.progress.getHearts()`, `s.profile.findSettings()`. Never import `db.ts` or Dexie. All three queries: `networkMode: "always"`, `staleTime: Infinity` for hearts, default for the others.
- **Query cache shapes (ADR-005, binding for every agent):** `["progress", courseId]` → `LessonResult[]` (raw results of the course, never a derived shape), `["hearts"]` → `HeartsState` (stored, not refilled), `["settings"]` → `Settings | null`. Derived values (`UserProgress`, completed ids, views) are computed in the hook or with `select`, never stored under these keys. PLT-008's `useCompletedLessonIds` must use the same query function and a `select`, otherwise the two caches overwrite each other.
- **Hook shape:** export `useProgressInputs(courseId)` → `{ status, results, hearts, goalXp, today, now }` (LES-010 needs the raw inputs) and `useUserProgress(courseId)` → `{ status, progress }` built on it with `useMemo(() => computeUserProgress(…))`. `status` is `"error"` if results or hearts fail; a settings failure falls back to the default goal. `progress` is `null` unless `"success"`.
- **`useLocalToday()`:** `timeZone = Intl.DateTimeFormat().resolvedOptions().timeZone`; state `today = toLocalDate(new Date(), tz)`; one `setTimeout` to the next local midnight (compute it as the first instant whose `toLocalDate` differs, robust to DST; cap the delay at 24 h and recheck), plus `visibilitychange` → recompute. Also return `now` refreshed on the same events so `refillHearts` isn't stale.
- **Edge cases:** results of another course ignored (filter by `courseId` even though the repository already filters, AC 6); duplicate result ids impossible (repository is idempotent) but count distinct `lessonId`s anyway; `today` earlier than a result's `localDate` (clock moved back) is handled by `computeStreak`; keep `completedLessonIds` in first-completion order for stable output.
- **Tests:** table-driven `progress.test.ts` with the GAM-002 `__tests__/fixtures.ts` builders, each output through `UserProgressSchema.parse`; perf case builds 1,000 results and asserts `performance.now()` delta < 50 ms. Hooks: RTL `renderHook` with a fresh `QueryClient` wrapper and `openLocalSession({ forceMemory: true })` (or a stub session); `vi.useFakeTimers()` + `vi.setSystemTime` for midnight; dispatch `visibilitychange` with `document.visibilityState` stubbed. `vitest --coverage` for criterion 14.
- **Dependency:** `@tanstack/react-query` and the `QueryClientProvider` in `src/app/providers.tsx` arrive with PLT-008. If you start first, test with a local provider wrapper; do not add the provider to `src/app` yourself.
