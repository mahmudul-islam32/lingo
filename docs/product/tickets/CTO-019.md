# CTO-019: Per-exercise outcomes on the device, ready for sync, and the review contracts
**Owner:** cto · **Priority:** P1 · **Depends on:** CTO-015, CTO-018 (same files: merge
CTO-018 first) · **Milestone:** v0.5.5 Smart review · **Decisions:** PD-065, PD-071 §2,
PD-079, PD-080, PD-081

## User story
As a learner, I want Polyglow to remember which exercises I got right or wrong so that a
review session can bring back the ones I need (US-SR-01, US-SR-02).

## Background
Today a finished session is saved as one `LessonResult` with counts only
(`firstTryCorrectCount`, `mistakeCount`). The per-exercise `ExerciseAttempt`s live in the
in-memory `LessonSession` and are dropped after the results screen. Smart review needs, per
answered exercise: which course, lesson and exercise it was, whether it was right the first
time, and when. Nothing is stored for results saved before this ticket, so review starts
empty for every learner and fills as they play (PD-080).

## Acceptance criteria
Names are proposals; the cto may rename them in the ADR. The behaviour is what is tested.

### Per-exercise outcomes
1. Every **finished** session (lesson, practice replay or review) stores one outcome per
   presented exercise, e.g. `ExerciseOutcome { lessonId, exerciseId, exerciseType, outcome }`
   with `outcome` one of:
   - `correct`: the first attempt was correct with no mistake (match pairs: no mismatch);
   - `incorrect`: at least one attempt on this exercise in the session had
     `mistake: true` (a correct retry later in the session doesn't change it);
   - `skipped`: skipped without an answer (listen without audio, "Can't speak now").
   Hidden exercises have no outcome. The date used for scheduling is the result's
   `localDate`, so no per-outcome timestamp is required (the ADR may add one).
2. `lessonId` is the **source lesson** of the exercise. In a review session the outcomes
   point to the lessons the exercises come from, not to the review.
3. The outcomes are saved **atomically with the session's result**: one Dexie transaction,
   one sync record, same idempotency key (`LessonResult.id`). Saving the same result twice
   stores the outcomes once (unit test).
4. **Shape choice is the ADR's.** Recommended (PD-079): an optional array on
   `LessonResult` (e.g. `exerciseOutcomes`), which needs no new Dexie table, no new sync
   kind and no new index. If the ADR picks a separate table and sync kind instead, it lists
   the Dexie version bump, the index, the repository method and the upgrade test.
5. Refinements (zod): at most one outcome per `(lessonId, exerciseId)` in a result; the
   number of outcomes ≤ `exerciseCount`; the number of `correct` outcomes =
   `firstTryCorrectCount` and of `skipped` = `skippedCount` when outcomes are present (if
   the existing counters are defined differently in an edge case, the ADR names it and
   drops that one equality). Fixture tests for each refinement.
6. **Compatibility:** results stored or queued before this ticket (no outcomes) still parse
   and still count for XP, streak, daily goal and path. `CONTRACTS_VERSION` stays `1`, or the
   ADR explains the bump and how queued `lesson_result` records with `schemaVersion: 1`
   still parse. Test with a stored v0.5.4 result.

### Review results
7. A result can be marked as a **review** session (e.g. `kind: "lesson" | "review"`, missing
   = `"lesson"`). The ADR fixes what a review result holds in `unitId` / `lessonId` (e.g.
   reserved slugs) so that no review result can be mistaken for a course lesson.
8. The contract documents the consumer rules (implemented in GAM-015): a review result
   counts for total XP, today's XP, the daily goal and the streak, and **never** adds a
   lesson to `completedLessonIds`, the path, the Practice list or the goal-plan count.
9. A **review item** type for the player and the route, e.g. `ReviewItem { courseId,
   unitId, lessonId, exercise: Exercise }`, plus the selection signature
   `SelectReviewItems` in `api.ts` (inputs: course, the course's results, today; output:
   ranked candidates `{ lessonId, exerciseId }` and `dueCount`). The full rule is written in
   the doc comment exactly as in GAM-015 criteria 1–6.

### Config
10. `GAME_CONFIG` gains `reviewSessionSize: 10` and `reviewIntervalsDays: [1, 3, 7, 14,
    30]` (strictly increasing positive integers), and `REVIEW_EXERCISE_TYPES` lists the
    types that can be reviewed: `multiple_choice`, `word_bank_translate`, `match_pairs`,
    `listen`, `cloze`, `choice`, `listening` (not `speak`, `task`, `explain`; PD-081).
    `GameConfigSchema` validates both new values.
11. Review XP and hearts reuse existing values: `xpPerLesson`, `perfectLessonBonusXp`,
    `heartsGainedPerCorrectAnswer`, `practiceCostsHearts` (review is practice, PD-079).
    No new XP constant.

### Backend and docs
12. Supabase: `lesson_results` stores the outcomes and the kind (e.g. a `jsonb` column with a
    CHECK on its shape, or a child table with RLS by owner). `migrate_guest_to_account`
    carries them. RLS unchanged in spirit (owner only). No migration is run against hosted
    Supabase.
13. An ADR (next number) records the shape, the outcome rule in criterion 1, the review-result
    rule in criteria 7–8, the item type, the config, the storage cost estimate (about 12
    outcomes per result) and the consumer changes for GAM-015, LES-023 and PLT-029.
14. `npm run typecheck`, `lint`, `test`, `build` pass; existing contract tests pass or are
    updated in the same PR, with the reason in the PR description.

## Out of scope
- Backfilling outcomes for results saved before this ticket (impossible: attempts were not
  stored; PD-080)
- Storing outcomes of quit or out-of-hearts sessions (PD-080)
- Any UI (GAM-015, LES-023, PLT-029); the selection rule's implementation (GAM-015)
- A server-side review schedule or sync of a schedule: the schedule is always derived from
  results on the device

## UX notes
No UI in this ticket. Mobile 375 px and accessibility: n/a (contract only); the consumer
tickets carry them. Learner-facing rule (PD-079): **review only brings back exercises you
have already answered, and it works like practice: free, at 0 hearts too, correct answers
earn hearts, XP as for a lesson.**
