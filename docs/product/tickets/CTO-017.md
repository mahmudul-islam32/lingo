# CTO-017: Contract for the goal date (`settings.goalPlan`, `GoalPlanStatus`, `computeGoalPlan` signature)
**Owner:** cto · **Priority:** P1 · **Depends on:** CTO-015 (start level) · **Milestone:** v0.5.4
Goal date · **Decisions:** PD-064, PD-071 §1

## User story
As a learner with a date in mind (a move, a course start, an appointment), I want Polyglow to
remember my target level and date so that the app can show how many lessons are left and what
daily goal gets me there; as a developer, I want one contract for the plan and its computed
status so that GAM-013, PLT-027 and LES-022 build against the same shape (US-GD-01 … US-GD-04).

## Acceptance criteria
Names below are proposals; the cto may rename them in the ADR. The behaviour is what is tested.

### Stored plan
1. `SettingsSchema` gets an optional field `goalPlan: { targetLevel: CefrLevel; targetDate:
   LocalDate }` (`CefrLevelSchema`, `LocalDateSchema` from today's contracts). A missing field
   means "no goal date". Settings stored before CTO-017 still parse (test like the CTO-015
   `startLevel` test); no Dexie version bump.
2. `goalPlan` is part of the learner-editable settings patch (today's `Pick<Settings, …>` in
   `api.ts`), and the patch can **clear** the plan (e.g. `goalPlan: null` removes it). A unit
   test shows set → clear → field absent (or `null`, as the ADR decides) after parse.
3. Schema tests: accepts `{ targetLevel: "A2", targetDate: "2027-03-12" }`; rejects an unknown
   level (`"D1"`), a non-ISO date (`"12/03/2027"`), a date-time string and a missing
   `targetDate`.

### Config
4. `GAME_CONFIG.goalPlanMaxDays = 730` (latest allowed target date = today + 730 days). The
   minimum is fixed by the rule "after today" and needs no constant. Lessons-per-day maths uses
   the existing `GAME_CONFIG.xpPerLesson` and `dailyGoalOptions`.

### Computed status
5. A `GoalPlanStatus` type (zod schema optional) with: `targetLevel`, `targetDate`,
   `lessonsLeft` (int ≥ 0), `daysLeft` (int, may be ≤ 0), `lessonsPerDay` (int ≥ 1, or `null`
   when `status` is `reached` or `date-passed`), `suggestedDailyGoalXp` (one of
   `dailyGoalOptions`, or `null` in the same cases) and `status`:
   `"on-track" | "raise-goal" | "tight" | "reached" | "date-passed"`.
6. `api.ts` documents the signature of the pure rule `computeGoalPlan` (implemented by
   GAM-013 in `src/features/gamification/rules/`), in the same style as the path rule:
   inputs = course (levels, units, lessons in order), completed lesson ids, `startLevel`,
   `goalPlan`, `today: LocalDate`, `dailyGoalXp`; output = `GoalPlanStatus | null`. The
   doc comment states the rule exactly as in PD-071 §1.3 (lessons counted, days, rounding,
   status thresholds) so GAM-013 has one source.

### Backend and docs
7. Sync readiness: either the Supabase settings table gets nullable columns (or a nullable
   JSON column) for the plan with RLS unchanged, or the ADR states that the column is added
   with v0.6.0 (PLT-010 / PLT-014) and lists it there. No migration is run against hosted
   Supabase (there is none yet).
8. A short ADR (next number) records the field, the clear semantics, the status names and
   why the status is computed on the device and never stored.
9. `npm run typecheck`, `lint`, `test`, `build` pass; existing contract tests pass unchanged.

## Out of scope
- The rule implementation and the Learn card (GAM-013)
- The Profile row, dialog and route wiring (PLT-027)
- The results-screen line (LES-022)
- A weekly plan, reminders, exam names or any paid entitlement (PD-071, PD-072)

## UX notes
No UI. Copy and states are defined in GAM-013, PLT-027 and LES-022.
