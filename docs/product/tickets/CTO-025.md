# CTO-025: Accounts groundwork: ADR-020, accounts flag, local Supabase test harness
**Owner:** cto · **Priority:** P0 · **Depends on:** CTO-003, CTO-018, CTO-019, CTO-021 (all
done) · **Milestone:** v0.6.0 Accounts and sync, **part A (local Supabase, no owner keys)** ·
**Decisions:** PD-085, PD-087

## User story
As a dev on v0.6.0, I want one agreed design for auth, sync and account switching and a local
Supabase I can test against, so that PLT-010 … PLT-018 can be built and accepted before the
owner's hosted project exists.

## Background
The schema, RLS and `migrate_guest_to_account` RPC exist (`/supabase/migrations`, ADR-003),
including `start_level`, `goal_plans`, `kind` and `exercise_outcomes`. `src/lib/sync` is empty.
Guests already enqueue every write in the Dexie `syncQueue`, which nothing drains yet.

## Acceptance criteria
1. **ADR-020 "Accounts and sync engine"** records, building on ARCHITECTURE §4 and §6:
   - where the Supabase browser client lives and the **accounts flag**: accounts are enabled
     only when `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are set at build
     time; otherwise the app is guest-only, shows no auth UI and makes **zero** requests to
     Supabase (today's production behaviour, PD-087);
   - a second flag for Google (e.g. `NEXT_PUBLIC_AUTH_GOOGLE_ENABLED`), so the button only
     shows when the provider is configured (PLT-011);
   - the `/auth/callback` route for email confirmation, password recovery and OAuth, and the
     rule that a `next` parameter is only followed when it is a same-origin path;
   - the push algorithm (ordering, idempotency, LWW, backoff, rejected vs. retried errors, 401
     handling) and the **column mapping** `LessonResult` ↔ `lesson_results` (incl. `kind`,
     `exerciseOutcomes`, `xp`) and `Settings` ↔ `settings` (incl. `startLevel`, `goalPlans`;
     never the legacy `goalPlan`, CTO-021);
   - the pull algorithm (cursors, paging past `max_rows = 1000`, merge into Dexie without ever
     deleting a local unsynced record) and one sync at a time per device across tabs;
   - account switching on one device: guest → account migrates (PLT-013); account → another
     account only after log-out (PLT-017); the log-out sequence.
2. **No goal plan or start level is silently lost on log-in** (product requirement, PD-087).
   Today `migrate_guest_to_account` replaces the whole settings row when the guest's
   `updatedAt` is newer, so a guest who onboarded today on a second device would wipe the
   account's goal plans. The ADR decides the rule (pm preference: merge `goal_plans` by course
   key, newer record wins per key; other settings newer-wins as today) and, if the RPC changes,
   a new migration implements it with a SQL or integration test.
3. `.env.example` lists the two public variables and the Google flag with the comment "public
   anon / publishable key only. The service-role key and the database password never go in
   the app, `.env.local`, chat, issues or CI logs." It shows how to fill them from
   `supabase start` for local development.
4. A documented local harness (README section or `docs/architecture/local-supabase.md`):
   start, reset and stop the local stack (`supabase start`, `supabase db reset`), where the
   local URL, anon key and the Inbucket / Mailpit mail UI are, and how e2e creates test users
   (local stack only).
5. A Playwright project (e.g. `accounts`, `npm run test:e2e:accounts`) runs against the local
   stack and **skips with a clear message** when it isn't running; the default e2e projects
   keep running without Supabase and keep passing. The ADR records whether CI runs the
   `accounts` project (`supabase start` in the workflow) or, if Docker isn't available in CI,
   who runs it before merge.
6. Database tests against the local stack cover: user A can't select or insert user B's rows
   in any table; `anon` sees nothing; replaying the same migration payload inserts no extra
   lesson result; a pushed duplicate result id is ignored; a stale settings update is skipped.
7. Contract additions the ADR needs (e.g. a `SyncPullResult`, auth error codes) are added with
   zod schemas and tests; `CONTRACTS_VERSION` stays 1 unless the ADR explains why not.
8. The "check your email" sign-up flow (email confirmation on, as on hosted, PD-087) can be run
   at least once against the local stack with the mail UI, or the ADR states why PLT-010 covers
   it with RTL only.
9. `npm run typecheck`, `lint`, `test`, `build` pass; hosted Supabase is not touched.

## Out of scope

- Auth screens and the sync engine itself (PLT-010 … PLT-018)

No screens. The flag rule (criterion 1) protects today's guest-only production build: nothing
in the UI changes until the owner's keys are set.
