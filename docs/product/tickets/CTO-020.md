# CTO-020: Document exercise-id uniqueness as a smart-review guarantee

## User story
As a learner, I want every exercise I answered to be able to come back in review, and the
"ready for review" count to match what I can actually play, so that the Review card never
promises more than the session gives me (US-SR-01, US-SR-03).

## Background
GAM-015 counts eligible exercises by `(lessonId, exerciseId)` and keeps one candidate per
`exerciseId`. LES-023 keys a review session by exercise id. Both are only correct if an
exercise id identifies exactly one exercise across every course. The content test from
CTO-008 already enforces that, but nothing tied the review code to it.

## Acceptance criteria
1. A content test that runs on every `npm run test` fails when one exercise id appears in two
   lessons of any course. It names each repeated id with its lessons, and it fails if it read
   no lesson files at all.
2. The guarantee is documented where the review contracts rely on it: the exercise `id`
   field, `ReviewSelectionSchema.candidates` and `SelectReviewItems` in the contracts.
3. ADR-019 states the consequences: a review session may key by exercise id, the dedupe per
   `exerciseId` never drops an eligible exercise for valid content, and `dueCount` /
   `eligibleCount` match the playable candidates. The schema stays total on invalid content.
4. `npm run typecheck`, `lint`, `test`, `build` pass.

## Out of scope
- Changing any id in `/content` (none repeats today)
- A runtime check in the app (the content test is the gate)

## UX notes
No UI. Learner-facing effect: the count on the Review card equals the number of different
exercises the review can play.
