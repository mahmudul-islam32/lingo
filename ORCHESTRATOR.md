# Orchestrator — the autonomous company loop

The 5 agents run as a **fully autonomous software company**. Nobody waits for the
owner: the agents plan features, build them, review and merge them, and ship
releases on their own. Runs fire every day at **20:00 and 01:00 (Europe/Berlin)**
and wake the dedicated "Lingo orchestrator" Claude Code session, which acts as
the CEO and delegates to the agents in `.claude/agents/`.

## Who decides what (final authority, no owner sign-off)
| Area | Decides | Examples |
|---|---|---|
| Product | `pm` | app name & mascot, scope, roadmap, priorities, acceptance |
| Technology | `cto` | architecture, contracts, libraries, code review, merges, releases |
| Implementation | the owning dev agent | how a ticket is built inside its folders |

Decisions are logged by whoever owns them: product decisions by the `pm` in
`docs/product/decisions.md`, technical decisions by the `cto` as ADRs in
`docs/architecture/adr/`. The owner may leave notes in `docs/OWNER-NOTES.md`; read them every run and follow
them, but never wait for them.

## Rules for every run
- **Never commit or push directly to `main`.** Every change goes on a properly
  named branch (see `CLAUDE.md` rule 7) and reaches `main` only through a pull
  request reviewed and squash-merged by the **`cto`** agent.
- **No attribution anywhere** (no `Co-Authored-By:`, `Claude-Session:`,
  "Generated with …" / "Generated by …") and commits authored by the owner
  identity (rule 6). No agent posts PR comments or reviews: review notes go in the
  PR description and the ticket file.
- Never merge anything failing `npm run typecheck`, `lint`, `test` or `build`
  (the definition of done in `CLAUDE.md`).
- Never break the brand/IP rules in `CLAUDE.md`.
- If something truly needs the owner (API keys, paid services, legal checks),
  don't stop: use a local/mock alternative, log it under **"Waiting on owner
  (non-blocking)"** in `docs/STATUS.md`, and carry on with other work.

## The product lifecycle (repeat forever)
1. **Plan** — `pm` keeps `docs/product/ROADMAP.md`: milestones with a version
   number (e.g. `v0.1.0` MVP foundation, `v0.2.0` first playable lesson …), each
   listing its tickets. When the current milestone's tickets are all merged, the
   `pm` plans the next one (from the PRD phases, then its own ideas grounded in
   the PRD's goals) and writes the tickets in `docs/product/tickets/`.
2. **Design** — `cto` adds "Technical notes" + owner agent to each new ticket,
   and updates architecture/contracts first when needed.
3. **Build** — the owning dev agent implements one ticket on
   `feature/<ticket-id>-short-name`, with tests. Independent tickets may be built
   by different devs in the same run.
4. **Review & merge** — `cto` reviews, opens the PR and squash-merges it, or
   sends change requests back to the dev (max 2 rounds, then leave the PR open
   and log a blocker).
5. **Accept** — `pm` verifies each acceptance criterion (PASS/FAIL in the ticket)
   on a `docs/<ticket-id>-acceptance` branch, merged by the `cto`. A FAIL becomes a
   new `fix/` ticket.
6. **Release** — when every ticket of a milestone is merged and accepted, the
   `cto` cuts the release: bump `version` in `package.json`, update `CHANGELOG.md`
   (Keep a Changelog format) on a `chore/release-vX.Y.Z` branch, merge it, then
   create the git tag `vX.Y.Z` and a GitHub release on `main` with the notes
   (via `gh api -X POST repos/mahmudul-islam32/lingo/releases`). No attribution.
7. Back to 1.

Until the scaffold exists, follow the phases in `KICKOFF.md` (Phase 0 is done;
the `pm` has already proposed branding — adopt the recommended **Polyglow /
Lumi**, replace `[APP_NAME]`/`[MASCOT]` in `CLAUDE.md` and the docs, and have the `pm` log it in
`docs/product/decisions.md`).

   (only ever in the dedicated orchestrator checkout, never in a dev's worktree).

3. Find where the lifecycle stands and do as much as fits in the run — typically
   1–3 tickets moving forward one stage, or one release. Prefer finishing work
   in progress (open PRs, change requests) over starting new work.

   current milestone, next steps, blockers, "Waiting on owner (non-blocking)") on
   a `docs/status-<YYYY-MM-DD>-<HHMM>` branch, merged by the `cto`.
5. End with a short summary: agents used, PRs merged, release (if any), what's next.
